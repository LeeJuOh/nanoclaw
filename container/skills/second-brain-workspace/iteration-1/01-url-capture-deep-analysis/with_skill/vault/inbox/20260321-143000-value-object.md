# Value Object — 동일성이 아닌 값으로 정의되는 작은 객체

*출처*: Martin Fowler | martinfowler.com

---

## 핵심 주장

- **Value Object는 동일성(identity)이 아닌 값(value)으로 동등성을 판단한다**: 두 Value Object가 같은 값을 가지면 같은 객체일 필요 없이 동등하다고 본다. 이는 Entity와의 핵심적인 차이점으로, 도메인에서 "누구인가"가 아니라 "무엇인가"를 표현하는 개념에 적합하다.
- **Value Object는 반드시 불변(immutable)이어야 한다**: 값이 변하지 않아야 공유 시 부작용을 방지할 수 있고, 동등성 비교가 안전하게 유지된다. 변경이 필요하면 새 객체를 생성하는 방식을 사용한다.
- **엔터프라이즈 애플리케이션에서 Value Object가 과소 사용되고 있다**: 개발자들이 모든 것을 Entity로 만드는 경향이 있어 불필요한 복잡성이 생긴다. Martin Fowler는 이를 업계의 고질적 문제로 지적한다.

## 주요 논거 및 근거

- Money, Date Range, Address 등 실생활의 직관적인 예시를 통해 "값으로 비교되는 객체"의 개념을 설명한다. 100원짜리 동전 두 개는 물리적으로 다르지만 같은 가치를 갖는다.
- DDD에서 Value Object는 Aggregate 내부에서 사용되어 별도의 식별자 관리가 필요한 Entity 수를 줄인다. 이는 도메인 모델의 복잡도를 직접적으로 낮춘다.
- 불변성을 유지함으로써 멀티스레드 환경에서의 안전성, 캐싱 가능성, 디버깅 용이성 등 실질적인 이점을 얻을 수 있다.

## 인사이트

개발자들이 모든 도메인 개념에 ID를 부여하는 것은 데이터베이스 중심 사고의 관성이다. "이 개념에 정말 식별자가 필요한가?"라는 질문을 먼저 던지면, 상당수가 Value Object로 더 간결하게 표현 가능하다. Value Object를 적극적으로 사용하는 것은 단순히 코드 스타일이 아니라 도메인 모델의 복잡도를 구조적으로 줄이는 설계 판단이다.

## 실용적 시사점

- 새로운 도메인 개념을 모델링할 때 "이것에 고유한 식별자가 필요한가?"를 먼저 질문하라. 필요 없다면 Value Object로 시작하라.
- Value Object는 불변으로 설계하고, 변경이 필요한 경우 기존 객체를 수정하지 말고 새 인스턴스를 생성하라.
- 기존 코드에서 Entity로 구현된 것 중 실제로는 값 비교만 필요한 것들을 Value Object로 리팩터링하면 모델이 단순해진다.

## 한계 및 열린 질문

- ORM과의 매핑에서 Value Object를 어떻게 영속화할지(임베디드 vs 별도 테이블)에 대한 실무적 가이드가 부족하다.
- 언어별로 Value Object 구현 패턴이 다르며(Java의 record, Kotlin의 data class, TypeScript의 readonly 등), 언어 특성에 따른 구현 차이를 다루지 않는다.
- Value Object가 커지면(필드가 많아지면) 불변성 유지의 비용이 증가하는데, 그 임계점에 대한 논의가 없다.
